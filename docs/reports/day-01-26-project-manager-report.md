## 5. 主要项目风险

### PR-001：Phase 2 安全闭环延期风险

级别：Critical

现状：

- Day 20-26 完成了租户与认证基础。
- RBAC、端点授权策略、审计仍未完成。

影响：

- Phase 2 无法 Accepted。
- 后续 Phase 的多云、FinOps、运营能力会建立在不安全的访问边界上。

管理动作：

- Day 27-30 不应插入非安全主线需求。
- 每个 Day 必须有拒绝路径测试和跨租户测试。

### PR-002：生产身份与开发身份混用风险

级别：Critical

现状：

- Azure Provider 当前仍依赖开发形态凭据。
- Microsoft Entra 用户登录不等于 Provider 运行身份生产化。

影响：

- 生产环境无法满足最小权限、审计、轮换和隔离要求。

管理动作：

- 将 Provider runtime identity 作为独立里程碑管理。
- 在未完成前，不允许对外宣称云操作生产可用。

### PR-003：租户隔离被误认为已完成

级别：High

现状：

- TenantContext 与 Repository 过滤已完成。
- 数据库层隔离、端点授权、审计和旧数据验证仍未完整闭环。

影响：

- 管理层可能误判为“多租户已完成”。
- 后续查询、报表、Worker 任务可能绕开应用层过滤。

管理动作：

- 文档和评审中统一口径为“租户隔离基础已完成，生产隔离未完成”。
- 将 RLS 或等效数据库层隔离列入后续 Phase 硬门禁。

### PR-004：成本数据可信度风险

级别：Critical

现状：

- 成本 POC 和 Cost ETL 基础存在。
- 成本语义、账期、币种、计费口径、修订、资源归因仍不足。
- sample fallback 仍被列为生产红线。

影响：

- 可能输出错误成本结论。
- 影响预算、优化、分摊和管理决策。

管理动作：

- 所有成本功能在未完成语义闭环前，只能标记为工程验证。
- 生产环境必须配置层面硬禁 sample fallback。

### PR-005：ETL 可靠性不足风险

级别：High

现状：

- Worker 注册与 ETL run 基础已完成。
- 调度、租约、并发互斥、checkpoint、恢复、告警尚未完成。

影响：

- 数据可能重复、遗漏、延迟或静默失败。

管理动作：

- 后续 ETL 施工必须先做运行模型，再做业务扩展。
- 所有后台任务必须具备 run id、状态机和失败追踪。

### PR-006：发布与迁移治理不足风险

级别：Critical

现状：

- 迁移宿主已建立。
- staging、artifact promotion、发布审批、回滚和数据库恢复未完成。

影响：

- 无法证明发布过程可控。
- 迁移事故会直接影响数据完整性。

管理动作：

- 建立独立发布里程碑。
- 每次 schema 变更必须关联迁移策略、回滚策略和备份策略。

### PR-007：运维不可观测风险

级别：Critical

现状：

- 当前主要证据来自本地测试和 CI。
- API、Worker、Provider、数据库、ETL 缺少统一指标、trace、告警和 SLO。

影响：

- 生产问题无法早发现、快定位、可追责。

管理动作：

- 可观测性必须与生产发布前置绑定。
- 不允许先上线后补 SLO。

## 7. 管理决策建议

### 决策 1：冻结 Phase 2 范围

建议：

- Day 27-30 只做 RBAC、端点授权、审计和 Phase 2 收口。
- 不插入多云、成本高级语义、前端、告警平台等非 Phase 2 内容。

原因：

- 当前最大生产阻断是安全闭环。
- 范围扩张会稀释关键施工资源。

### 决策 2：建立“生产可用”用词审批

建议：

- 所有文档中，只有通过对应 Phase gate 的能力才能写“生产可用”。
- Day 1-26 的成果应表述为开发基线、工程治理、认证基础或租户基础。

原因：

- 当前文档已经较清晰，但项目历史较长，仍需防止口径漂移。

### 决策 3：将风险台账作为验收输入

建议：

- 每个 Phase 完工报告必须引用风险台账和生产缺口台账。
- 每个 Accepted 必须说明关闭了哪些风险，保留了哪些风险。

原因：

- 这样可以避免“完成 Day”被误解为“关闭全部风险”。

### 决策 4：建立证据留存规则

建议：

- 长期验收证据放入 `docs/` 或 commit 记录。
- 临时日志和中间输出允许放在 `tmp/`，但不能作为唯一验收证据。

原因：

- 当前文档整改已经把长期文档收敛到了 `docs/`、`construction/` 和根 README。
- 后续复盘必须能从仓库中直接追溯。

## 8. PM 结论

项目 Day 1-26 的推进质量在“工程建设”层面是正向的，尤其是 Phase 1 的工程治理和 Phase 2 的租户身份基础，为后续生产化打下了结构基础。

但项目当前的管理重点必须从“继续加功能”转为“关闭生产控制红线”。Day 27-30 是项目从工程骨架进入安全闭环的关键窗口。只要 RBAC、端点授权、审计和 Phase 2 gate 没有完成，项目就只能定位为研发阶段平台，不能定位为生产级云治理平台。
